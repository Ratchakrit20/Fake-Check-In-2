# Database schema

The application uses SQLite by default for local development and can be configured for PostgreSQL. Image bytes are stored outside the database; the default local storage is `data/images`, and `images.storage_path` stores the path or key used by the configured storage backend. Object storage is optional and is not required by the local setup.

## Core tables

| Table | Purpose | Important columns |
| --- | --- | --- |
| `analysis_jobs` | One processing request from this UI or an external system | `id`, `status`, `total`, `processed`, `created_at`, `started_at`, `completed_at`, `duration_seconds`, `error` |
| `images` | An uploaded evidence image | `id`, `original_filename`, `source_job_number`, `source_checkin_date`, `source_technician_id`, `source_job_type`, `source_captured_at`, `ai_metadata_json`, `image_quality_status`, `image_quality_reason`, `near_black_ratio`, `storage_path`, `file_size`, `width`, `height`, `mime_type`, `sha256`, `phash`, `phash_rotations_json`, `created_at`, `analyzed_at`, `analysis_status` |
| `analysis_job_items` | Links each submitted image to a processing job | `job_id`, `image_id`, `position`, `status` |
| `image_embeddings` | Versioned vector embedding per image/model and orientation | `image_id`, `embedding`, `model_name`, `model_version`, `configuration_version` |
| `pairwise_results` | One normalized relationship result per image pair | `image_a_id`, `image_b_id`, `phash_distance`, `dino_similarity` (legacy column used for SSCD similarity), SIFT/RANSAC metrics, `relationship_score`, `relationship_level`, `details_json`, `created_at` |
| `export_reports` | One generated PDF and Excel summary | `id`, `date_from`, `date_to`, `pdf_path`, `summary_xlsx_path`, `created_at` |
| `export_report_images` | Immutable snapshot of evidence images included in a report | `export_report_id`, `image_id`, `source_job_number` (Customer ID), `source_checkin_date`, `source_technician_id`, `group_id_snapshot` |

## Relationships and indexes

```text
analysis_jobs 1 ──< analysis_job_items >── 1 images
images        1 ──< image_embeddings
images        1 ──< pairwise_results >── 1 images
export_reports 1 ──< export_report_images >── 1 images
```

Important uniqueness rules include one job item per `(job_id, position)`, one embedding per `(image_id, model_name, model_version)`, one result per normalized image pair, and one snapshot row per `(export_report_id, image_id)`. Pair image IDs are stored in normalized order to avoid duplicate rows for the same pair. Report snapshot image references restrict deletion so evidence used by a generated report is not silently removed.

`images.source_job_number`, `images.source_checkin_date`, `images.source_technician_id`, and `images.source_job_type` are indexed so external systems can retrieve evidence by job number, check-in date, technician, or job type. Upload parsing recognizes `new`, `ma-mat`, `ma-new`, and `ma-splice` job types and extracts EXIF capture time when available. Excel summaries are generated by the reusable `summary_export_service` from configurable column definitions; detection categories and subcategories are row data so other detection modules can reuse the same exporter.

`images.ai_metadata_json` stores per-image `lat_long` and `datetime` detection boxes and confidence scores from the configured `lat-long/v1` model. Datetime boxes identify SOA images in the Dashboard and PDF; lat-long boxes are retained alongside them so both classes from the same inference are persisted. Metadata version 2 marks records containing both classes, so historical datetime-only metadata is eligible for backfill. This is a nullable column on the existing `images` table; no new technician or snapshot table is needed. To scan historical images, finish any active analysis job, then run `python -m backend.app.workers.scan_soa_metadata` from the project root. The command skips records with current metadata and refuses to run while an analysis job is active. It does not rerun image-pair analysis or change relationship results.

`images.phash` stores the original-orientation pHash. `phash_rotations_json` stores pHash values for supported rotations for candidate search. SSCD embeddings are stored in `image_embeddings`; rotated embeddings use the same table and identify orientation in `model_name` (for example, a `__rotcw_<angle>` suffix). The unique key is per image, model name, and model version.

The SIFT feature cache is a bounded filesystem cache under `data/cache/sift` by default. It is a performance cache, not a database table; removing it only causes SIFT features to be computed again.

`images.image_quality_status`, `image_quality_reason`, and `near_black_ratio` record the pre-matching quality gate on the existing image row. A small grayscale thumbnail is checked before pHash. If the fraction of pixels with luminance at most 16 reaches the configured threshold (default 90%), the image is `UNVERIFIABLE`. It remains in storage and the database, but is omitted from pHash and SSCD/FAISS candidate indexes and reportable groups; no image-pair matching is run for it. Historical rows with a null quality status are assessed once before the next batch builds its candidate indexes. This is a metadata-only scan, not pair reanalysis, and adds no new table.

The reuse Excel summary has one row per reportable image pair. Each row includes the pair's classification, both filenames, and source metadata for image A and image B. A/B identify the pair order only; they do not claim which file is the original. Capture time comes from EXIF when present, with the filename's check-in date shown when the historical file has no EXIF time.

`source_job_number` is displayed in the UI and PDF as **Customer ID**. The database column deliberately retains its old technical name so existing records and integrations continue to work.

All API presentation layers resolve source metadata through
`backend/app/services/image_source_service.py`. It reads persisted source
columns first and falls back to `parse_source_reference()` only for historical
records with missing values. This keeps Dashboard, Groups, Export PDF, and
analysis submission checks consistent while retaining backward compatibility.

## Relationship eligibility and score policy

Dashboard, Groups, and PDF Export use the same classification policy:
`exact_file`, `same_image`, and `edited_or_cropped`. The shared list is in
`backend/app/services/relationship_policy.py` so the three surfaces cannot
silently drift apart.

`config/default.yaml` → `relationship.report_min_relationship_score` is an
optional second filter applied after classification. It is `0.00` by default,
so every eligible classification is currently shown and exportable. The score
is still stored for every pair and remains available for audit/debugging.

To make later filtering stricter without changing code, restart the backend
after changing this value:

| Value | Effect |
| --- | --- |
| `0.00` | No score filtering; all eligible classifications are grouped and exportable. |
| `0.30` | Light filter; excludes low-confidence eligible pairs, but may split a weakly connected group. |
| `0.65` | Previous stricter filter; fewer false-positive links, with a higher risk of omitting borderline reused images. |

Increasing the value can remove a linking pair and therefore split one image
group into several groups. Lowering it can merge groups through weaker links.

## Resumable analysis jobs

`analysis_job_items.status` is the durable checkpoint for batch analysis. Each item moves from `QUEUED` to `PROCESSING` and then `COMPLETED`; a resumed job processes only items not marked `COMPLETED`. If a worker shuts down during pair analysis, the job is marked `INTERRUPTED` and can be resumed through `POST /api/v1/jobs/{job_id}/resume`. This avoids recomputing completed images after a restart or power interruption.

## Export report snapshot

When a PDF is generated, `export_reports` records the actual first and last check-in dates represented by its evidence, rather than only the filter dates selected in the UI. `export_report_images` stores every image included and its `group_id_snapshot`. This preserves the evidence and group membership that existed at export time, even if relationship grouping changes later.

## Schema initialization and adding a new field

At startup, `backend/app/db/session.py` creates missing tables with SQLAlchemy `Base.metadata.create_all()` and runs the application's explicit additive column/index upgrades for existing databases. The project does not currently use Alembic migrations; `create_all()` alone does not add columns to existing tables. Keep schema updates additive and update the upgrade logic in `session.py` along with the SQLAlchemy models.

For every new persisted field, update these layers together:

1. `backend/app/db/models.py` - add the SQLAlchemy column and its index/constraint when needed.
2. `backend/app/db/session.py` - add a safe additive upgrade for existing databases. `Base.metadata.create_all()` only creates a new table; it does not add a new column to an existing table.
3. `backend/app/domain/schemas.py` - add request/response validation when the field crosses the API boundary.
4. Relevant API route/service - read/write the field, for example `backend/app/api/routes/batches.py` for image ingestion or `backend/app/api/routes/exports.py` for report data.
5. `frontend/src/api/client.ts` and the relevant page/component - add the TypeScript type and visual control only if the UI needs it.
6. This document - keep the production schema and field purpose current.

## External API boundary

External websites must communicate only through `/api/v1`, never by sharing the database. Submit images to create a job, poll `/api/v1/jobs/{id}`, and retrieve group/image data from the API. This keeps the processing service replaceable and lets the UI evolve independently.

## Production requirements

- For a multi-process or multi-machine production deployment, use PostgreSQL and shared storage (for example, S3 or MinIO) so API and AI worker processes can access the same image files. Add a versioned migration system such as Alembic before deploying schema changes; this is a recommendation, not the current migration mechanism.
- Use a persistent worker queue such as Redis/Celery when scaling beyond the current local worker arrangement.
- Add an `external_request_id` and `source_system` to `analysis_jobs` before integrating a caller, then make the pair unique for safe retries.
- Store credentials and connection strings in environment variables or a secret manager; never commit them.
- Version models and threshold configuration with each result, which the existing embedding/result metadata already supports.
